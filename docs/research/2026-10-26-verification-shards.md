# 回归验证超时与完整分组

PR #19 在提交 `12b9a60b8aa0339b06c2e9f1b33d48ff5cb67abb` 的 Python 3.9 固定依赖检查中失败：[PR 运行日志](https://github.com/StephCpa/AgentSec/actions/runs/40399475799/job/121841173748)。30 个历史入口和 7 个模型均通过；单一 `review_regressions` 子进程在 2026-10-26 21:00:55 UTC 开始、21:30:55 UTC 超时，返回码 124。日志中已有 187 项测试通过，停在后续模块的类级初始化之前，没有断言失败记录。同一提交的 Python 3.12 两次完整检查均通过，但整体已耗时约 37–38 分钟。

原因是随着恢复、清理、窗口生命周期实验加入，全部回归共用的 1800 秒限额不足。不能把超时视为成功，也不能以减少场景解决。

## 修复

- 每个回归模块使用独立 `unittest discover` 进程，保留模块的 `setUpClass` 与全部测试方法；不拆分或重复类级实验。
- 完整检查清单为 30 个历史入口、21 个回归模块（原 225 项回归加 6 项验证器测试）、7 个模型，共 58 个命令。
- GitHub Actions 对 Python 3.9 固定依赖及 Python 3.12 升级依赖分别运行四组，按完整有序清单的索引模 4 分配。各组的并集等于全套，互不重叠；未设 fail-fast，不因一组失败取消其他组。
- 每个命令仍限制 1800 秒，每组仍限制 45 分钟。失败与超时继续使该组失败；超时日志明确写出原因。没有更改协议、持久化策略或实验矩阵。
- 本地默认串行执行全部 58 个命令，不需要指定分组。使用 `--shard-index N --shard-count 4` 可复现某一组。

`run.json` 保留全部源码摘要，新增完整命令清单、分组参数、所选命令、`full_suite_selected` 及逐项耗时/超时标记。分组报告的 `passed` 只指该组，不能当作全套成功；全套 CI 要求同一提交两种环境的八组均通过。历史证据报告保持原样，其旧格式和测试数量仍对应当时提交。

## 覆盖与失败行为

新增验证器测试核对四组的无重复完整覆盖，并用 unittest 实际发现的测试 ID 比较旧的一次性发现和新的逐模块发现，要求多重集完全相同。其他测试覆盖无效/空分组拒绝、`--only` 原语义保留、非零退出失败、超时失败及日志保留。这些检查验证运行器，不代替协议测试。

修复后验证状态以对应 GitHub Actions 运行结果为准；本说明不将尚未结束的 CI 标为通过。
