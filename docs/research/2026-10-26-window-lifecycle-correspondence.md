# 一个位置的窗口补充与连续恢复中断

接收方清理前缀后释放的位置，应能用于后续业务；已确认的旧事实、预算与首次结果不能因此重新生成。本轮在 `af7eb1a354ef47d7aa92849981746d24c45eaefd` 上增加一个显式受限配置，将清理、待交付的新操作、窗口满拒绝和连续恢复中断接入同一条公开轨迹。

协议与持久化策略保持原实现。原清理配置仍要求所有操作已有最终结果，并拒绝清理后的新业务；本轮通过独立子类扩展实验范围。恢复子进程的业务禁用守卫增加准备清理和确认清理两个方法。完整边界见[配置契约](../../outputs/agent-cryptography-design-20261025/prototype/window-lifecycle-contract.json)。

## 场景和判别点

可信初始化使用一个路由、接收窗口 `window=1`，最多两个操作。先在时间 100 完成计数操作 A、接收及发送方确认。之后有两类调度：

| 计划 | B 出现的时间和行为 | 需要区分的结果 |
|---|---|---|
| after_retire_count | A 清理并恢复后，在 130 提交 B 计数 | 新业务可使用释放的位置 |
| after_retire_histogram | 同上，B 为直方图 | 不同机制仍只调用一次 |
| after_retire_cancel | 同上，B 在 L1 前取消 | B 为 WITHHELD，不占接收位置、不采样；A 历史不变 |
| queued_count | 在 110 完成 B 计数并尝试交付，A 尚未清理 | 首次交付因窗口满而拒绝；恢复后的容量取决于清理是否已权威提交 |
| queued_histogram | 同上，B 为直方图 | 已准备的大结果信封与原预算保持 |
| queued_expire | 在 110 完成并准备 B，直到 180 才恢复 | 原期限仍为 170；终止消息绑定原信封，首次事实为 CLOSED |

A 的清理发送在三个位置真实退出：接收方删行后、见证接受后、本地清理提交后。前者恢复旧窗口，其余恢复已推进的 floor。不是把退出位置从实际存储状态推断出来再提供给生成器，而是预先固定公开环境计划。

每次分别从现有副本或空白新副本开始，在 `after_recovery_delete`、`before_recovery_commit`、`after_recovery_commit` 三个恢复钩子依次退出，再重复一遍，共六次。每次都实际启动子进程并核对退出码 96；原清理退出码为 97。最后另建一个继续执行业务的恢复副本。

本配置的可信调度器在显式恢复成功前不继续业务。即使一次恢复已在本地提交但返回丢失，模型仍只输出恢复不可用；它不据此重新采样或改写权威。这是本实验的调度边界，不能推广为所有部署都必须经过同一个通知 API。沿用的 `RECOVERY_CUT.operation` 字段在这里携带公开路由别名 `root`，不是业务操作编号。

恢复后，排队计划在重试 A 的清理前再次尝试 B。若 A 的清理未提交，此时仍应窗口满；若已提交，B 可以先占用释放的位置。随后旧清理 offer 重试返回当前检查点，不能误删 B。B 的首次交付再重试一次，验证窗口满时已有事实仍可返回原结果，而不是被当作新事实拒绝。

完成 B 后精确重放原签名 SUBMIT，并重放旧 A 的交付请求。普通 B 的确认完成后再次清理到序号 2，再查询和重放两条旧事实。取消计划只清理到 1；B 不产生第二条接收方事实。

## 构造性观察与 R15

[公开生成器](../../outputs/agent-cryptography-design-20261025/prototype/window_lifecycle_simulator.py)只接收公开设置、命令、时钟、故障计划、批准输出和显式签名资源。真实响应、SQLite 内容、见证头及私有随机带不会进入生成器。驱动在执行实际方法前记录命令，再逐字节比较生成的公开观察。

新事件 `DELIVERY_REJECTED` 带原签名请求和原因 `V2_RECIPIENT_WINDOW_FULL`。其状态效果分开处理：发送方已经准备信封和 handoff；接收方没有新增首次事实或回执；但经过认证的业务拒绝仍持久化 observed 时间和一次见证提交。模拟器内部复用“准备完成、没有接收事实”的逻辑转移；内部 `PACKET_LOST` 不是对外报告的丢包事件。

R1–R8 继续核对批准机制、预算、公开调度、准备对象、接收历史、发送确认及最终顺序。清理退出保留 R14，重复恢复退出保留 R12。本轮增加 R15：

- 当前 live 行数等于历史 `high-floor`，且介于 0 和 1。
- 已完成操作的 operation、job、charge 和 publication 行保持原始字节；原票据身份、结果摘要和期限保持不变。
- 已确认发送归档的完整原始行保持不变，包括原确认事实和回执密文。
- 已有 FINAL 行保持不变，允许新操作追加后续行。

共享账户可以因为 B 的合法预留、消费或取消而变化；R2 检查其精确金额关系，不能将上一轮的“冻结全部账户”原样用于新业务。R15 的不透明字节比较只在检查器内部进行，不把密文摘要、随机带或未发布结果写入公开轨迹。归档中的 R15 摘要仅覆盖公开窗口、已冻结对象编号及比较通过标志。

## 局部转移义务

令 H 为历史首次事实序列，h 为其最大序号，f 为接收方清理前缀，L 为接收方当前 live 映射。目标关系是 `L = H|(f,h]`、`0 <= h-f <= 1`，同时发送方已确认归档和 FINAL 已有前缀只增不改。以下是需要被运行证据支持的局部推导，并非对任意实际执行的完整归纳证明。

| 转移 | 保持关系的条件 |
|---|---|
| 空窗口接收新事实 | 新序号必须 h+1，且 h-f<1；插入事实和推进 h 在同一权威事务中提交 |
| 满窗口的新序号 | 不改 H、h、f、L；允许 observed 时间与见证日志推进 |
| 已有 live 事实重试 | 不再插入，不改首次结果与首次时间；回执绑定本次挑战 |
| 清理到 t | t 不超过发送方已确认前缀；核对原前缀根后原子删除 L 中序号不超过 t 的行并推进 f |
| 旧 offer 重试 | t<=f 时不删除新 live 行；返回当前 floor/root/high，发送方按原归档核对 |
| 旧交付重放 | 序号<=f 时拒绝，不能在已释放位置复活旧事实 |
| 见证接受前清理退出 | 原权威镜像仍同时保存旧 L 和 f；未提交的部分删除不进入关系 |
| 见证接受后清理退出 | 权威镜像同时保存新 L 和 f；本地落后副本必须经新鲜性检查或恢复 |
| 恢复反复中断 | 权威不变；本地镜像和 anchor 只能为恢复前或恢复后的完整组合；逻辑业务状态不前进 |

接收方局部归纳还不足以完成整个系统证明：还需证明任意允许命令都维持发送确认前缀与归档根、授权与原批准输出绑定，并将公开时序、长度、可用性以及密码学/DP 资源纳入同一个关系。这里用固定计划核对这些局部情形与实际代码一致。
