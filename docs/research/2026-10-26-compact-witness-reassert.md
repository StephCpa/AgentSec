# 保留提交语义的紧凑见证请求

前一轮确认：已提交槽或公开请求的精确重试不会重复计算，但仍会提交一份完整见证镜像。本轮新增默认关闭的 `reassert` 扩展，用于候选镜像摘要与预期旧摘要相同的 CAS。它保留写权限检查、版本推进、幂等请求 ID 和提交历史，只省去向见证重新传送同一镜像，以及更新见证 `image` 列的 SQL 写入。

这不是只读缓存命中。不同尝试仍使用不同请求 ID，每次成功都推进见证序号；如果返回值丢失，本地锚点即使拥有相同镜像摘要，也必须识别序号落后并恢复。协议不把两次独立尝试合并成一次，也不通过 `head` 的读取权限代替 `cas` 的写权限。

## 接口与事务规则

可信配置需同时设置服务端 `allow_reassert=True` 和客户端 `compact_reassert=True`，两者默认均为 `False`。不自动协商，也不在失败时回退。原始帧和可选压缩帧均可承载该请求；本轮成本测量使用原始帧。

客户端仍接收完整候选镜像，计算其摘要。仅当摘要等于 `expected_digest` 时使用空正文的 `reassert`；其他情况继续使用完整 `cas`。实际账本保护逻辑保持原样：事务开始、提交时各构建并检查一次完整本地镜像，提交回执仍必须是预期序号加一及候选镜像摘要。

`reassert` 元数据包含相同的 namespace、随机挑战、旧序号、旧摘要和请求 ID，正文长度固定为 0，正文摘要固定为空字节串的 SHA-256。服务端在一个 `BEGIN IMMEDIATE` 中按以下顺序执行：

1. 按当前 namespace 和证书指纹检查原有 `cas` 权限与撤销状态。
2. 查询历史请求 ID。相同逻辑 CAS 返回原回执；基准或结果摘要不同则拒绝。
3. 对新尝试，要求当前序号和摘要都精确匹配，防止旧版本或 ABA 状态被当作当前状态。
4. 在同一写锁下读取并校验留存镜像的摘要，损坏镜像不能获得新的成功提交。
5. 序号加一，保留镜像字节及摘要，插入原格式提交元数据，然后提交。

签名回复继续绑定方法、namespace、挑战、请求元数据摘要和 TLS 请求者。客户端额外核对成功序号等于 `expected_seq + 1`、摘要等于 `expected_digest`，且回复正文为空。只读 observer/restorer 角色不能因为正文为空而获得写权限；撤销检查发生在历史回执查找之前。

同一个逻辑 CAS 可在完整 `cas` 与 `reassert` 之间重传同一请求 ID，因为现有幂等契约绑定的是 namespace、基准序号/摘要和结果摘要。改变结果内容或基准仍冲突。不同尝试必须使用新 ID，此规则没有改变。

## 与完整 CAS 的对应关系

设当前权威状态为 `(s,d,I)`，满足 `hash(I)=d`。完整 CAS 以相同镜像为候选、新请求 ID 为 t 时，结果为 `(s+1,d,I)`，并追加提交行 `(s+1,d,d,t)`。紧凑请求在相同基准下产生相同状态与提交行。历史精确重试和冲突使用相同的判定条件；授权仍在同一事务内执行。

将客户端的“摘要相同”推广为“镜像字节相同”，依赖现有图像摘要的抗碰撞假设。有限实验直接核对了字节相等；这里没有完成一般密码学归约。留存镜像的校验能拒绝内容与摘要不一致的存储损坏，但不能替代见证不可回滚、诚实签名或跨主机持久化保证。

有限枚举使用两个独立的内存 SQLite 见证：一方始终执行旧的完整 CAS，另一方在摘要匹配时执行新方法。六种操作模板包括相同镜像、新镜像、旧基准、原请求重试、冲突请求 ID 和错误摘要，枚举长度为 4 的全部 **1,296 条序列**。每步比较返回值/错误及所有 head/commit 行，**5,184 次状态比较全部一致**；同时检查另一 namespace 没有变化。这不是任意深度或并发模型检查。

16 项专项测试还覆盖真实 mTLS、并发竞争、授权与更新持有同一写锁、握手后的撤销、旧成功回执的权限检查、篡改/重放回复、默认关闭且不回退、压缩帧组合、留存镜像损坏，以及无状态变化提交的未知结果恢复。后者注入服务端分派前/后连接丢失和本地提交前异常，没有新增真实进程死亡或断电实验。

## 实际成本对照

实际公开网关在进程内处理已签名 `POLL` 的精确重试，见证经真实 loopback mTLS 访问。每组先完成计数或四桶直方图任务，再增加 0、16 或 64 次新的轮询日志，冻结同一镜像，对普通/紧凑模式交替运行 24 对缓存重试。计时只包含被测缓存调用，排除夹具准备、审计、恢复和模型检查；性能运行期间没有同时运行本地测试矩阵。

六组共 288 次被测缓存调用；每次仍产生一个见证提交和两个完整本地镜像构建，累计分别为 288 与 576。请求帧字节统计包含 head 和写请求的应用帧，位于 TLS 包装之前，不是 TLS 记录字节或物理网络/磁盘计量。表内中位数使用每种模式 24 个样本，p95 使用最近秩定义；单次本机实验没有置信区间或生产负载保证。

请求帧减少约 99.2%–99.7%，而调用耗时中位数仅下降约 3.9%–6.0%。两个直方图配置的 p95 反而上升，因此不能宣称所有延迟分位数都改善。完整镜像构建、TLS 建连、见证写事务和提交元数据仍有成本。

每组额外发起一个新 `POLL`，确认它因新增日志继续使用完整 `cas`；逐字节检查权威镜像保持预期；生成公开轨迹并核对最终 R1–R8；从见证恢复新副本后再核对相同状态关系。公开消息生成器没有获得紧凑请求的私有状态输入。该检查覆盖这些缓存重试工作负载，未验证完整网络时序/长度观察的隐私。
